## Workloads

- **`spsc_throughput`**: One producer, one consumer, as fast as they can go: kItems ints through one queue. The consumer spins on an empty queue. Measures throughput under saturation; latency here would only measure how far behind the consumer falls, so none is reported.
- **`spsc_latency`**: One producer, one consumer, at a fixed rate well below either queue's capacity: one item every kIntervalNs. Each item is the time it was pushed, so the consumer can measure how long it waited in the queue. Reports the latency distribution, the number the project's motivation rests on: p50, p99, p99.9 and the worst case.
- **`spsc_payload`**: spsc_throughput with a 64-byte record instead of an int, so each push and pop copies a cache line. Shows whether the substitution's advantage holds when the payload, not the synchronisation, starts to dominate, and that it applies to a user-defined element type at all.
- **`spsc_same_thread`**: One thread is both the producer and the consumer: it pushes a batch, then pops it all, kRounds times. The verdict is still SPSC (one thread pushes, one thread pops; they happen to be the same), and this is the case a bounded ring cannot take: with a batch larger than the ring, a push that waited for room would wait forever. The substitute is unbounded, so it must complete. With no second thread there is no contention at all, so this measures the queues' raw cost per operation.
- **`mpsc_control`**: The control: two producers, one consumer. The verdict is MPSC, so --select-queue-impl must leave the queue alone, and run.sh fails if it does not. Baseline and optimized should then be the same program and measure the same, which bounds how much of the other workloads' difference is noise. There is no direct variant: spsc_queue is not safe with two producers.
